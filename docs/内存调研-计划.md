# 内存占用调研：能不能「只跑点开的功能」

> 这次只做了调研和实测，**代码一行没改**（探针是新增的测试工具，不影响主程序）。
> 下面每个数字都是这台机器上跑出来的，命令在最后。

## 一、先说结论

**你的直觉方向对，但机制不对。**

- 「只加载点开的东西」在**控件层面几乎省不到内存**：四个折叠区加起来 297 个元素，全拆掉只回收 **84 KB**，占主窗内存的 **0.09%**。
- 真正吃内存的不是「你没看的那些控件」，而是 **WPF 把窗口画到屏幕上这件事本身**：主窗从「构造完」到「显示出来」，内存从 31 MB 涨到 60 MB，**+27 MB**，翻了一倍。
- 所以真正有效的做法不是「按需加载控件」，而是 **「不用的时候把主窗整个销毁，要用再建」**——能省 27 MB（约一半），代价是下次打开要等 1 秒。
- 你担心的卡顿：**延迟加载控件几乎没有卡顿风险**（开一个子窗口 1.6–40.9 ms，期间 0 次 GC），**但收益也几乎没有**。而重建主窗 1049 ms，会明显顿一下。

一句话：**这个改造能做，但省的不是你以为的那 2 MB，而是那 27 MB，而且要靠销毁窗口而不是懒加载控件。**

## 二、实测数据

### 分段（Private Bytes，进程真实占用）

| 阶段 | Private | 增量 | 说明 |
|---|---|---|---|
| 空进程（只有 .NET 运行时） | 8.5 MB | — | 底 |
| 起了 WPF Application | 11.0 MB | +2.5 | |
| 装好主题令牌 | 11.5 MB | +0.5 | |
| **空窗口基线（只有一个 TextBlock）** | **23.5 MB** | **+12.0** | **WPF 的固定成本，跟我们写了多少界面无关** |
| 建完主窗（未显示） | 31.2 MB | +7.7 | 我们自己的 581 个元素 + 数据 |
| **主窗显示出来** | **60.0 MB** | **+28.8** | **渲染管线、字体光栅、纹理、交换链** |
| 主窗隐藏（托盘形态） | 56.6 MB | −3.4 | 隐藏只还回一点点，大头留着 |

真机实测（`发布\Dragon-Butler-win-x64-portable\Dragon Butler.exe`，启动 10 秒后稳定）：
**Private 51.7 MB / 工作集 108.9 MB / 31 线程 / 776 句柄**，40 秒后再测无变化（不涨，说明没有明显泄漏）。

### 子窗口（每个都是新建 → 布局 → 关掉回收）

| 窗口 | 建的时间 | 内存增量 | 关后残留 |
|---|---|---|---|
| 依赖 | 14.2 ms | 0 KB | −472 KB |
| 配置组切片 | 6.4 ms | 192 KB | 296 KB |
| 按日计划 | 11.3 ms | 128 KB | 264 KB |
| 挂机日历 | 12.3 ms | 648 KB | 784 KB |
| 今日运行 | 40.9 ms | 200 KB | −156 KB |
| 日志规则 | 5.0 ms | 128 KB | 192 KB |
| 迷你浮条 | 2.2 ms | 64 KB | 144 KB |
| 开跑前体检 | 4.5 ms | 128 KB | 200 KB |
| 出门前看一眼 | 9.2 ms | 256 KB | 328 KB |
| 跑完收拾一下 | 5.6 ms | 192 KB | 264 KB |
| 配置组合 | 18.2 ms | 132 KB | 204 KB |

**十一个窗口全加起来约 2 MB。** 就算全部改成「点开才建」，最多也就省 2 MB——而它们本来就是 `ShowDialog()` 时才 new 的，**现在已经是按需创建了**。

### 折叠区拆解（决定性的一测）

主窗 581 个元素里，四个折叠区占 297 个：

| 区域 | 元素数 |
|---|---|
| 高级设置（折叠） | 70 |
| 系统（折叠） | 73 |
| 通知（折叠） | 95 |
| 工具设置（折叠） | 59 |

把四块从视觉树上整个摘掉、强制回收：**回收 84 KB**（拆前 90 MB）。

原因：`Visibility="Collapsed"` 省的是**布局计算**，不是对象内存。控件对象、样式、模板、资源引用一个都不会少。要真省，得让他们压根不被 new 出来——那需要把 XAML 拆成 UserControl 再延迟实例化，工程量不小，换来 84 KB。

### 卡顿风险的量化

| 操作 | 耗时 | 分配 | 期间 GC 次数 |
|---|---|---|---|
| 开「今日运行」 | 3.7 ms | 177 KB | 0 |
| 开「开跑前体检」 | 2.5 ms | 106 KB | 0 |
| 开「迷你浮条」 | 1.6 ms | 47 KB | 0 |
| **销毁主窗再重建并显示** | **1049 ms** | — | — |

前三项：**延迟加载这些窗口不会卡，一次 GC 都不触发。** 分配量只有 47–177 KB，连 Gen0 的门槛都够不着。

最后一项才是真的会顿一下——**但它就是方案本身**，想省 27 MB 就绕不过这个 1 秒。

### 一个顺手查出来的问题

主窗关掉后**默认不会被销毁**：`Window_Closing` 里 `StayInTray` 为真时 `e.Cancel = true; Hide();`——这是设计好的托盘行为，不是 bug。但也意味着**主窗在托盘形态下一直占着那 28 MB 渲染成本**。

另一条：四个 `DispatcherTimer`（`_scheduleTimer` / `_countdownTimer` / `_groupScanTimer` / `_uiRefreshTimer`）的 `Tick` 闭包抓着窗口本身，**窗口关了 timer 不停，对象就永远回收不掉**。实测：不停 timer 直接关窗，弱引用仍然存活；先停 timer 再关，**能回收**。这条现在没暴露，但做方案 B 之前必须补。

## 三、三个方案

### 方案 A：什么都不改（成本 0，收益 0）

现在的占用是：托盘常驻 **51.7 MB Private / 108.9 MB 工作集**。

判断标准：对一个装了 .NET 8 桌面运行时的 WPF 常驻程序，这个数字**不算高**。对比一下：一个空的 WPF 窗口就 23.5 MB，Chrome 一个标签页 80–150 MB，Electron 应用起步 120 MB。

**如果你的目标是「让 8 GB 内存的机器跑得动」，现在就已经跑得动了。**

### 方案 B：托盘形态下销毁主窗（推荐，但要接受 1 秒）

- 点 X / 最小化到托盘时：先把四个 timer 停掉、解除静态事件订阅、`StayInTray` 那套逻辑改成真的销毁，只留托盘图标 + 哨兵 + Webhook。
- 双击托盘：重建主窗（实测 **1049 ms**），期间显示一个极简的「正在打开…」。
- **预期省 28 MB Private / 约 50 MB 工作集**（从 52 降到 24 左右）。
- 代价：每次打开要等 1 秒；托盘里的「打开主界面」响应变慢；如果这 1 秒里队列正在跑，界面状态要重建（`QueueService.CurrentToolId` 这些是静态的，不受影响，但要验证）。
- 风险：中等。`StayInTray` 是既有行为，改了要重新验「关窗后队列还在跑」「关窗后哨兵还在看」「关窗时正在弹对话框」。

### 方案 C：把折叠区拆成 UserControl 延迟实例化（不推荐）

- 省 84 KB，工程量是「把四块 XAML 拆出去 + 懒加载 + 状态同步」。
- **投入产出比极差。** 除非将来这些折叠区长到几百个元素，否则不值得。

## 四、我的建议

**先做方案 B，但拆成两步：**

1. **第一步（低风险，先做）**：补「关窗即停 timer + 退订事件」这个收尾。它本身不省内存（因为现在就 Hide 不 Close），但它是 B 的前置条件，而且能修掉一个潜在的泄漏源。**这一步可以独立提交，有探针能断言。**
2. **第二步（中风险，要先给你看效果）**：真的销毁/重建。做之前我会先做一个开关（默认关），你试过再决定要不要默认开。

**方案 A 也完全合理**——如果你的真实目标是「低配机器能用」，51.7 MB 不是瓶颈，瓶颈可能是磁盘（自解压 62 MB）和启动时间（593 ms 构造主窗）。这两个方向可能更值得做。

## 五、需要你决定的

1. **要不要做方案 B**？做的话，我能省 28 MB，但打开要等 1 秒。这个交换你接受吗？
2. 如果你更在意的是「低配机器能不能跑」，我可以改去测**启动耗时**和**磁盘占用**，那两个数可能比内存更影响体验。
3. 方案 B 做成**默认开**还是**默认关 + 设置里可开**？我倾向后者。
