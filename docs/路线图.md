# 路线图：原神生态的空白点，以及本项目要填的那一块

> 这份文档回答三个问题：**市面上那些受欢迎的项目都做了什么？还有什么是没被实现的？龙管家接下来该往里加什么？**
>
> 结论先行：BGI 把「游戏里怎么打」做到了极致，但「什么时候该跑、跑没跑完、失败了怎么知道、被打断怎么接着跑」这一圈没人管。这就是本项目的战场。
>
> 数据快照：2026-11-05，来自 GitHub API 与 BetterGI issue 库。

## 一、这份调研是怎么做的，以及它的边界

先说清楚证据从哪来，免得把推测当事实。

**能核实的**：

- GitHub API 拉取的星数、issue 正文、issue 标签与状态、评论原文、reaction 数——这些都是可直接点开复核的。
- BetterGI 文档（bettergi.com）与各项目 README。

**核实不了的**，如实交代：

- B 站、贴吧、NGA、米游社的评论区**没有系统抓取**——贴吧返回 403，Reddit / NGA / 知乎直连被墙，本次环境里 `web_search` 也不可用（无 API key）。所以本文里**没有任何一条结论是「评论区呼声很高」这种来源**，凡说到"用户想要"的地方，出处都是 GitHub issue。
- 各个工具在具体机器上的**实际失败率**。这类数据只有作者自己跑得出来。

**一条方法论上的自我提醒**：GitHub issue 有个天然偏差——会提 issue 的人，是被 bug 咬到的人，不是想要新功能的人。所以"某个需求零 issue"**不能**直接推出"没人需要"，只能推出"没人为此专门开过 issue"。本文按这个尺度写，遇到零 issue 的地方会明说是推测。

### 功能拆解：它们具体有这些能力

**BetterGI（执行层，最完整）**

自动拾取、剧情跳过与邀约、一条龙、秘境、地脉、幽境危战、首领、钓鱼、七圣召唤、伐木、音游、走图采集、JSON 脚本系统、配置组调度器、键鼠录制、自动战斗、命令行入口（`--startGroups`）、阶段通知、跑完关机。

它的边界（官方 issue 与文档都承认）：**无内置定时**、**无真正的多账号**、遇到被顶号弹窗不暂停、失败时"跳过或中断"未实现。

顺带说个细节，能看清这块的真空程度：在 [#846](https://github.com/babalae/better-genshin-impact/issues/846) 下面，有人问「每日凌晨四点自动运行一条龙」怎么做，回答是另一位用户接的——「可以用 windows 计划任务实现」。**用户给用户的答案，不是官方给的方案。**

**March7thAssistant（同层里做得最好的）**

日常、周常、模拟宇宙、货币战争、抽卡导出 UIGF、消息推送、体力恢复到指定值后自启、跑完关机，支持云星铁无窗口或 Docker 运行。

**定时、自启、通知三件事它做得最完整**，这是本项目最值得学的部分。它的边界：多账号要手动切换、无后台挂机方式、配置导入导出缺失。

**ok-ww（唯一同时做了多账号 + 计划任务的）**

全角色自动战斗、一条龙、刷声骸、4C、深塔、多账号、计划任务、最小化后台运行。

它的边界很典型：**切号时卡死**、**任务失败不退出游戏**、无邮件通知、后台点击依赖真实 HID 鼠标。

**Snap.Hutao.Remastered（工具箱，不是自动化）**

程序启动与更新、祈愿记录、成就、深渊、剧诗统计、养成计算、圣遗物评分、AI 分析、插件 SDK、自动连点、webhook 推送。**不需要游戏窗口**，因为它根本不动游戏。

### 哪些已经被做好了，本项目不该重复

| 能力 | 谁做好了 | 本项目的态度 |
|---|---|---|
| 视觉识别的基础动作（拾取/跳过/战斗/走图） | BGI | 不碰。这是执行层 |
| 任务编排 + 脚本仓库 | BGI 调度器 | 不复刻。我们做它外层的"什么时候跑" |
| 命令行 / 开机自启 | BGI、M7A | 已有（`AutoStartHelper.cs`），继续用 |
| 通知通道 | 大家都做了 | 已有 11 个渠道（`NotifyService.cs:20`），不再加 |
| 跑完关机 / 睡眠 | BGI、M7A | 已有（`AfterRunAction`） |
| UIGF / GOOD 数据标准 | wish-export、yas | 不涉及。本项目不解析游戏数据 |
| 面板与评分查询 | 胡桃、miao-plugin、GenshinUID | 不做。不登录、不读账号 |

一句话总结这张表：**大家把"工具"做满了，"编排"只有两家，而"编排出问题之后怎么办"一家都没有。**

### 一个反证，值得单独记下

调研里最有价值的一条是**没找到东西**：

> 「跨设备查看进度面板」在 BGI issue 库里查不到专门记录。

这不是遗漏——用户要的是「人不在电脑前，能知道跑完没有」，而推送通知（企业微信/飞书/钉钉/Telegram/Bark，甚至 Gotify、Qmsg）已经解决了它。所以：

- ❌ 不做独立手机 App、不做重型网页看板、不做 Telegram 双向 Bot
- ✅ 只做「手机扫一眼状态」这种一屏能看完的东西，且不出本机局域网

注意这里的分寸：这是**推断**，不是统计结论。零 issue 也可能只是因为大家已经用通知凑合习惯了。

### 明确不碰的两块

- **自动寻路做主线**：BGI [#49](https://github.com/babalae/better-genshin-impact/issues/49)，2023-11 提出，维护者当时的原话是「遇到存在纵深的地区就没那么好用了……这也是未来的方向，但不知道最终效果是否理想」，三年过去仍是 open；后续评论里有人提到字节的 Lumine 试过，结论是「不好搞」。
- **账号密码自动登录**：BGI [#1076 [feature]自动登录](https://github.com/babalae/better-genshin-impact/issues/1076) 至今 open，维护者原话是「这个功能，对于软件和用户来说是有风险的，我不太想做」；[#1140](https://github.com/babalae/better-genshin-impact/issues/1140)、[#1208](https://github.com/babalae/better-genshin-impact/issues/1208) 两个同类请求已被关闭。而同库 [#2395](https://github.com/babalae/better-genshin-impact/issues/2395) 想要的恰恰相反——**检测到登录界面就发通知并停手**。后者才是安全的做法，本项目站这一边。

这两条有个共同点：**碰了就要为别人的账号安全负责**。本项目的立场是不碰账号。

## 四、筛选门槛

每个候选功能必须先过四道闸，否则不做：

1. **零依赖**——不得引入任何 NuGet / npm / 新运行时。CI 的依赖审计步骤会直接拦下（见 `.github/workflows/build.yml`）。
2. **可断言**——必须能在 `tests/CoordinatorProbe` 里写出机器可验的断言，进 CI 跑。写不出断言的功能说明需求本身没想清楚。
3. **不碰执行层**——不做任何 CV、不做游戏内操作，只碰进程、信号、文件、HTTP。
4. **优先复用现成件**——先看仓库里有没有写了没接上的代码。本轮就找到一处（见 F2）。

## 五、功能清单

### P0 · v1.6「不再漏」——可靠性闭环

#### F1 定时补跑窗口

**治的病**：睡过了就永远不跑。

**现状缺陷（可验证）**：`Dragon Butler/MainWindow.xaml.cs:372` 的 `CheckSchedule()` 要求 `now.Hour == ScheduleHour && now.Minute == ScheduleMinute` 严格相等，且只记 `_lastScheduleRun`（`:71`）的**日期**。电脑睡眠、程序没开、上一轮还没结束——跨过那一分钟，今天就永久错过。

**作用**：定时到点没跑成，在窗口内补跑一次，并在界面说明「这次是补跑的」。

**落点**：
- 新增 `Dragon Butler/SchedulePlanner.cs`：纯函数 `Decide(settings, now, lastRunAt) → (ShouldRun, Reason, NextDue)`。把判定从 UI 线程抽出来，才能单测。
- `Dragon Butler/AppState.cs:51-55` 旁新增 `ScheduleCatchUpMinutes`（默认 120，0=关）与 `LastScheduleRunAt`（精确到分钟，取代「只记日期」的语义）。
- `MainWindow.xaml.cs:372` 改为调用 planner，保留 `QueueService.IsRunning` 与度假模式两道既有闸。
- `MainWindow.xaml:843-918` 定时卡概览页，在倒计时下方加一行小字说明补跑窗口，沿用 `TbCountdown` 现有字号配色。

**用法**：默认开。早上开机发现昨天该跑没跑，会补跑并记日志「定时：补跑（计划 08:00，实际 09:12）」。设置里可改窗口或关闭。

**验收**：Probe 新增 `schedule` 模式，断言三组——计划 08:00 / now=09:05 / 上次未跑 → 触发；now=11:00 → 不触发；now=08:00 且今天已跑过 → 不触发。

#### F2 「接着跑」

**治的病**：被打断只能从头再来。

**现成件**：`Dragon Butler/GroupArchive.cs:183-189` 的 `GetUnfinished()` 已经写好「今天尚未结束的组名列表（供"继续跑"）」，**但全仓库零引用**。这是白捡的。

**作用**：上一轮被停止 / 失败 / 关机打断后，一键只跑没完成的那些，已完成的组不重跑。

**落点**：
- `Dragon Butler/QueueService.cs` 在 `StartAsync`（`:115`）旁新增 `StartContinueAsync()`：用 `GetUnfinished()` 与当前启用队列求交，走同一条 `RunListAsync`（`:226`）。`QueueTrigger` 枚举加 `Continue`。
- `MainWindow.xaml` 队列卡（`:794` 起）加一颗幽灵次按钮，复用 `:82` 现成样式。
- `App.xaml.cs:117-121` 托盘菜单加一项，仅在存在未完成组时可见。

**用法**：失败通知里出现「接着跑」提示，点一下只补没跑完的。

**验收**：Probe 新增 `resume` 模式——StubTool 跑一半被 kill → `GetUnfinished()` 有记录 → 断言只有未完成项被执行。

#### F3 失败现场包

**治的病**：出事了只能问人「当时啥情况」。

**作用**：失败 / 悬置 / 挂起时自动打包：最近 200 行日志、脱敏后的 settings、进程列表、屏幕截图、版本号。排查不用靠回忆。

**落点**：新增 `Dragon Butler/IncidentBundle.cs`（`System.IO.Compression` 是 BCL，零依赖）；在 `QueueService.FinishQueue`（`:699`）与 `HandleStall`（`:364`）调用；输出到 `全部日志\incidents\yyyyMMdd-HHmmss\`；截图复用 `ScreenshotMonitor.cs:88` 已具备的抓图能力；`AppState` 加 `IncidentBundleEnabled`（默认开）与保留份数（默认 10）。

**用法**：无需操作。失败通知正文末尾带文件夹路径。

**验收**：Probe `failed` 模式跑完断言三件事——目录存在、含 `log.txt` 与 `env.json`、`env.json` 里**不含** token / password / 邮箱明文。

#### F4 通知说清「为什么」

**治的病**：现有 `QueueService.cs:699-749` 五个通知分支，全部以「详情见软件日志」收尾。人在外面收到这句话，等于没收到。

**作用**：换成真正的原因——最后一条错误行、退出码、悬置 / 挂起的具体判据。

**落点**：`QueueService.cs:699-749` 改文案生成；`SentinelService.cs:252 HandleCrash` 把 `BgiExited` 的退出码带进通知；`NotifyService` 结构不动，只换正文。

**验收**：Probe `haltedlog` 模式断言通知正文包含日志命中行原文。

#### F5 重试退避可配

**现状**：`QueueService.cs:471` 固定 `1 + RetryCount`，`:501` 固定 `Task.Delay(3s)`——3 秒后硬撞第二次，对「游戏加载慢」这类失败毫无意义。

**落点**：`ToolProfile.cs` 加 `RetryDelaySeconds`（默认 3）与 `RetryBackoff`（bool，指数翻倍）；`RunItemAsync`（`:467-510`）按配置睡；`CustomToolWindow.xaml` 加两个输入框，复用 `:300` 输入框样式。

**验收**：Probe 断言第 2 次启动与第 1 次的间隔 ≥ 配置值。复用 `QueueService.IntervalOverride`（`:110`）同款注入点思路。

### P1 · v1.7「看得见」——远程与统计

#### F6 本机控制 API

**背景**：BGI [#2328](https://github.com/babalae/better-genshin-impact/issues/2328) 要四条命令（优雅停止/启动、跑完即停、跑指定任务、查状态）仍 open。历史上 [#1873](https://github.com/babalae/better-genshin-impact/issues/1873) 实现过远程控制，2025-07-13 当天合并，**一周后的 2025-07-20 被 [#1892](https://github.com/babalae/better-genshin-impact/issues/1892) 整体 revert**，原因是引入了 ASP.NET Core 运行时依赖——绝大多数用户得额外装 runtime，官方打算等 .NET 升级改 SelfContained（本体 +70MB）再放。

**作用**：让外部脚本或 AI 助手能查状态、开跑、停止、只跑某个工具。

**落点（必须遵守既有铁律）**：`Dragon Butler/WebhookHub.cs:10` 写着验收标准「全库 `new HttpListener` 仅存在于 WebhookListener 内部一处」。**不新增监听器**，改在 `WebhookListener.cs:60` 的 `Loop` 里按路径路由：`/webhook` 原样保留，新增 `/api/status|start|stop|run`。鉴权走 `X-Butler-Token`（32 hex，首次启动生成入 settings），默认只绑 `127.0.0.1`。

这个设计恰好绕开了 #1892 的回滚原因：`HttpListener` 是 BCL 自带的，零 NuGet、零新运行时、体积不变。

**用法**：`curl -H "X-Butler-Token: …" http://127.0.0.1:18235/api/status`

**验收**：Probe 新增 `api` 模式，断言 200 / 401（缺令牌）/ 404（未知路径）；开关关闭时 `/api/*` 一律 404。

#### F7 手机只看面板

**背景**：BGI [#3772](https://github.com/babalae/better-genshin-impact/issues/3772) 主张用 BCL 的 `HttpListener` 绕开 #1892 的依赖问题。但按上面第一节的推断，独立看板大概率是伪需求，所以只做**一屏的只读页**。

**作用**：手机连家里 WiFi 打开一个地址，看到「跑到第几个 / 还要多久 / 上一条事件」。

**落点**：`WebhookListener` 增加 `/` 返回内嵌 HTML（一个 C# 字符串常量，**零 npm、零构建**）；纯只读无控制按钮；默认仍绑回环，用户显式打开「局域网可访问」才绑 `0.0.0.0`，界面提示可能需要 `netsh http add urlacl`。

**验收**：Probe 断言 `/` 返回 200 且 `Content-Type: text/html`；开关关闭时只监听回环。

#### F8 周报

**作用**：本周跑了 N 次、成功率、平均耗时、失败最多的工具。数据源是 `GroupArchive` 已有的按天记录（`GetDay` `:167`），零新增采集。

**落点**：`MorningReport.cs` 旁新增 `WeeklyReport.cs`，复用 `BuildSummary`（`:49`）的措辞风格；`AppState` 加 `WeeklyReportEnabled`。

**验收**：`BuildWeekly(IReadOnlyList<GroupRecord>)` 是纯函数，Probe 直接断言字符串。

## 七、排序理由

为什么 P0 是这五项，而不是「更有意思」的那些：

1. **每一项都在修一个已经存在的缺口，不是造新概念。** F1 改的是 `CheckSchedule()` 的判定逻辑；F2 接的是 `GetUnfinished()` 这段死代码；F4 改的是五个通知分支的字符串。改动面小，风险可算。
2. **每一项都能写进 CI 断言。** 这是本项目的验收前提——用户不读代码，只跑 CI 和看实物，所以「说不清怎么验」的功能一律不立项。
3. **它们共同拼成一条闭环**：定时到点（F1）→ 跑不完能接着跑（F2）→ 失败了知道为什么（F4）→ 现场能查（F3）→ 重试有策略（F5）。

P1 是「人不在电脑前」的延伸：外部能控制（F6）、手机能看（F7）、一周能回顾（F8）。它们依赖 P0 的数据，所以排在后面。

## 八、如何参与验收

本项目由 AI 实现、由人验收。每项功能的验收方式是固定的三步：

1. **看 CI**：`.github/workflows/build.yml` 会跑依赖审计、`-warnaserror` 构建、以及对应的 Probe 断言。红就是没做完。
2. **看实物**：`dotnet build` 后跑起来，界面上应该能摸到这项功能。
3. **看日志**：`全部日志\` 里应该有这项功能的轨迹行（本项目所有行为都留痕）。

一项功能如果这三步都过不了，就不算完成，无论代码看起来多漂亮。

## 九、第二批：补的不是洞，是「让人眼前一亮」（F9–F15）

前面 F1–F8 是往漏的地方补——用户不会因此夸一句，只会觉得「本来就应该这样」。这一节换一个问法：**什么东西能让第一次打开的人「哇」一下，而且明天还会接着用？**

### 这批功能是怎么挑出来的

调研通路说明（和第一节一样，先把边界说清）：`web_search` 在本机没有 API key，`web_fetch` 直连 GitHub 与外网被解析策略挡住，所以本轮所有外部证据都来自 `gh api`（仓库搜索 + README 原文）。评论区、视频弹幕这类「呼声」仍然采不到，**下面没有任何一条结论来自「网友说想要」**。

证据来源是四个被大规模使用的桌面工具，而不是原神圈子里的小项目：

| 参考对象 | ★（2026-11-06） | 语言 | 借的是它的哪个设计 |
|---|---|---|---|
| microsoft/PowerToys | 140,612 | C# | Always on Top、Awake、Command Palette——**一次按键解决一件事**，不是又一个要配置的面板 |
| Flow-Launcher/Flow.Launcher | 15,965 | C# | 算完直接进剪贴板、Game Mode（玩游戏时自动接管热键）、预览面板 |
| JosefNemec/Playnite | 14,460 | C# | 游戏库式的一屏总览 |
| ShareX/ShareX | — | C# | 自动捕获（定时/事件触发）、自定义工作流与热键 |

这些工具的共同点只有一条，也是这一节的选题标准：**功能要短到一句话说得完，用户在听到的那一刻就能判断自己要不要。**

同时按第四节的四道闸过滤，被筛掉的比留下的多：

- ❌ 桌面自动化里的「AI computer use」（`topic:desktop-automation` 前四名 31,820 / 16,823 / 14,393 / 11,069★ 全是这个方向）：要吃模型、要联网、要 CV，撞死在第一道闸上。
- ❌ 截图 OCR 取字（PowerToys Text Extractor 的思路）：同样要吃 OCR 引擎。
- ❌ 插件系统 / 脚本扩展点：要设计契约，等于把自己变成一个平台，风险不可算。
- ❌ 主题包市场：没有用户就没有回路。

留下来的七项，按「要不要动窗口」分两档。

### P0′ · v1.6 加料：不用打开窗口就知道（F9–F12）

#### F9 全局热键

**为什么眼前一亮**：这是 BGI [#3772](https://github.com/babalae/better-genshin-impact/issues/3772) 三百多行诉求里**最便宜、最不需要开端口**的一半——不用 HTTP 服务、不用局域网、不用鉴权，就能回答「现在什么情况」。而且实现成本极低：抓屏代码本来就在仓库里跑着。

**风格与风险**：

- 边界声明：它读像素但不做任何识别判断，**不违反「不碰执行层」**。
- 隐私：截图只落本地并在用户明确点击时生成，不做定时自动抓（那已经是 `ScreenshotMonitor` 的职责，两者不合并）。

## 十二、一件必须记住的本地验证前提

`CrashGuard.Install()` 在启动时会调 `LogService.CheckLastExit()`：如果日志目录里有历史日志但**没有** `last_exit_ok` 标记，就会弹一个模态窗「检测到上次为异常退出」。这个弹窗会挡住启动流程——程序窗口不起、端口不监听，看起来像「新功能没生效」。

本地手工验证（尤其是用 `Start-Process` 起进程再用 `Invoke-WebRequest` 打接口）必须先写标记：

```powershell
Set-Content -Path "$binDir\全部日志\last_exit_ok" -Value "2026-11-06 20:20:00" -Encoding ASCII
```

正常使用不受影响（正常关机会自己写这个标记）；这是**无头验证**才需要的人工前置。CI 不跑 GUI，所以碰不到。

### 实现时才想清楚的点

**依赖不抛异常，也不做并行。** 环（A 等 B、B 等 A）不当作错误抛出——真抛了用户看到的就是一次崩溃，而他只是勾错了两格。做法是拓扑排序时把环上的项原序排到末尾，`TryOrder` 用 `stuck` 把它标出来，保存时界面拦一道「依赖绕成圈了」；真跑起来时依赖门（`QueueGraph.Gate`）对它永远判 `Waiting`，超时后按策略跳过并说清「等 X 先跑成」。并行则根本不考虑：同一时间只跑一个工具是 `RunCoordinator` 的「宁等勿进」，改成并发要把整个状态机重写。

**依赖门的 `done` 初值取今天的台账，不是空集。** `RunListAsync` 用 `new HashSet<string>(RunJournal.DoneToolsToday())` 起手，这样「今天 BGI 已经跑成了，现在点接着跑」不会因为 BGI 不在这一轮里而永远等不到它。反过来，被前置检查挡掉（`PreCheck` Skip）的项会被记进 `failedThisRun`——它本轮不会再有结果，依赖它的一项不该干等。

**策略写错一律按「跳过」处理。** `ShouldAbortOnDependencyFail` 只认字面量 `Abort`。理由是这两个选项的代价不对称：错当跳过，最多少跑一项、日志里还有一行；错当中止，整条队列停在半夜。

**切片为空 ≠ 不跑，而是「沿用全局」。** 这是整个 P2 里最容易埋雷的一条：升级上来的老 `settings.json` 里没有 `Groups` 字段，读出来是空列表，如果把它理解成「一个组都不跑」，所有老用户升级当天就会看到 BGI 什么都没干。所以 `GroupSlicing.Effective` 的语义是「本项写了就用本项，没写就用全局」，「一个都不跑」根本没有表达方式。

**认不出的组名直接丢掉，但只在识别成功时丢。** `BgiDiscovery.Scan()` 失败（路径没设、目录不在）时 `Groups` 是空的，此时若拿空集合当白名单，用户辛苦写的组名会被全清掉。所以 `Sanitize` 的第二参数为 `null` 或空集合时**不做过滤**，只有真识别到组名才剔除已删除的组——宁可少跑一个组，也不要让 BetterGI 因为一个不存在的组启动失败。

**版本检查只读文件、只在成功后记录。** `BgiVersionGuard` 不发一个请求（有断言扫源码确保 `BgiVersionGuard.cs` 里没有 `HttpClient` / `WebRequest` / `DownloadFile`），只读 `BetterGI.exe` 的 `FileVersionInfo`。记录时机是 `RunItemAsync` 里 `State == Done` 之后——更新坏了的那一版不该被写成基线，否则下次真出问题时反而不会提醒。

**版本比对前先削掉尾巴。** `Normalize` 去掉 `+buildhash` 与 `-beta` 后缀，只比 `1.2.3` 这一段。BGI 同一个版本重新编译一次哈希就变，按全串比会天天误报「版本变了」。

**读不到版本就闭嘴。** `Judge` 里 `current` 为空直接返回 `Unknown`，`AnnounceBgiVersion` 对 `Unknown` 不做任何事。这条功能唯一的失败模式就是「因为不知道而乱报」，宁可少提醒一次。

### 为什么是这两项

**G1 的证据是全场最硬的**：BGI 官方播放量最高的十几条实机演示里，一半以上是「收益播报」体——「9.6 小时 40 万摩拉」132,511 播放、「AAA 狗粮批发 72 分钟 12.5 万摩拉」97,419 播放。有人在简介里自己口算「一趟 10-12 小时，摩拉收益 26-28w」。也就是说**官方用视频标题替玩家回答「这趟值不值」，而没有任何工具帮他自己算**——但我们手上是同一批日志。

**G5 便宜到不该犹豫**：二十行代码，复用 `SchedulePlanner` 已有的判断，解决的是「静默失败」——定时没跑成时，用户第二天只看到「上次执行：两天前」，不知道是没开机还是跑挂了。

### 实现时才想清楚的点

**解析规则必须写成「几乎不可能误伤」的形状。** 这是整批里最容易做错的地方：BGI 的日志格式没有任何兼容承诺，脚本输出更是谁的都可能。所以只认「标签 + 明确分隔符（`+ ＋ x × : ： = ＝`）+ 数字」和「数字 + 摩拉」，**明确不认**「摩拉收益 26-28w」「12.5万摩拉」这类带区间或单位的写法——它们出现在视频标题和聊天里，不该出现在日志行里。断言里专门钉了这几条「不认」，因为**误伤比漏算糟得多**：漏算只是少报一个数，误伤会让用户看到完全假的钱。

**没有做「省了多少钱」的换算。** 候选文档里原本写了「按代肝市场价 35–120 元/月换算」。实现时砍掉了：代肝价格是市场行情、会变；更主要的是，**把爱好换算成钱这个判断该由用户自己做**，软件替他算一次，以后每次数字都像个承诺。

**`Take()` 必须清零。** 不清零的话，第二趟队列会把第一趟的收益再报一遍，而用户完全没有办法发现这件事——他不会记得上一次的具体数字。断言里专门有一条「Take 取走即清零」。

**账本坏了不能影响开跑。** `EnsureLoaded` 里任何异常都只记一行日志并重置为空账。这个文件是程序自己写的，但它可能在断电时写坏；收益统计出错不该导致队列跑不了。

**探针绝不能写用户的真实账本。** 这是实测时踩到的：第一版断言直接调 `AddToDay(DateTime.Today, ...)`，跑完发现真实 `config\harvest.json` 里多了测试数据，今天的「本月累计」变成 129,834。加 `HarvestLedger.PathOverride` 把探针重定向到临时文件、跑完删掉。**测试污染用户数据是比功能算错更难查的问题**——用户不会怀疑到这个文件上。

**G5 的判断完全复用 `SchedulePlanner`。** 做法是「把『现在』换成昨天必定错过的时刻，去问它为什么没跑」，得到的原因就是当时的原因。这样不需要新增任何状态字段，也不需要「在错过的那一刻记一笔日志」——那一刻电脑很可能根本就没开。代价是判据和 F1 绑在一起：以后 F1 的语义变了，这里得跟着改。断言里钉了四种情形（定时关着 / 没勾星期 / 昨天该跑 / 昨天不该跑），其中「昨天不在计划里就不说话」这条防的是「每天都提醒一遍昨天没跑」这种烦人错误。

四个工具：`butler_status`（只读）、`butler_start`、`butler_stop`、`butler_run`（要 `toolId`）。协议只实现 `initialize` / `tools/list` / `tools/call` / `ping`。

### 实现时才想清楚的点

**这不是「又一个 HTTP 接口」，是同一扇门上的第四条路。** `/api/status`、`/api/start`、`/api/stop`、`/api/run` 已经在了，MCP 只是让 AI 客户端知道「这些能力叫什么、参数怎么写」。所以它复用同一个监听端口、同一把 32 位令牌、同一套 404 策略——多开一个端口就是多一个要被记得关的东西。

**改 `Route` 委托签名，而不是加第二个监听器。** `WebhookListener.Route` 原来是 `Func<path, query, token, result?>`，MCP 是 `POST` + JSON-RPC，拿不到请求体就没法解析。加第四个参数把整条链路都改一遍，但换来的是「全库只有一个文件 `new HttpListener`」这条铁律继续成立——probe 里那条断言到现在还在跑。

**通知（没有 `id`）回 202 空体，不回 JSON-RPC 响应。** 这是 JSON-RPC 2.0 的规矩：通知不需要应答。实现上要额外小心 `Content-Type`——空体时不能设成 `application/json`，否则客户端可能把空字符串当解析失败。

**`id` 原样回显，数字不能变成字符串。** 用 `JsonDocument.Parse(idJson).RootElement.Clone()` 把收到的 id 原始 JSON 存下来再写回。看起来是小事，但有些客户端按 `id` 做类型严格匹配，回错了它就不认这次响应。

**畸形请求回错误码，不 500。** 六种情况分得清楚：坏 JSON `-32700`、非对象 `-32600`、缺 `method` `-32600`、未知方法 `-32601`、`tools/call` 缺 `params`/`name` `-32602`、未知工具则是**工具级错误**（`result.isError = true`）而不是协议错误——因为「你要的这个工具不存在」在 MCP 里属于正常结果的一部分，客户端应该能读懂并转述给人。

**`butler_run` 收 `toolId` 不收 exe 路径。** 这一条是本项目所有对外接口共用的红线：能指挥的只有「队列里已经有的东西」，没有「执行任意程序」这种口子。

实机验法（本地无头要先把 `last_exit_ok` 补上）：

```powershell
$h = @{ "X-Butler-Token" = "<令牌>" }

  -Body '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' -ContentType "application/json"
```

两个坑：`Invoke-WebRequest -Method Head` 在非交互 PowerShell 里会报「处于非交互模式」；`curl.exe -w "%{http_code}"` 在这里返回 `000`。检查 HTTP 状态码用 `HttpClient.SendAsync` 最稳。

### 没做的部分，以及为什么

- **resources / prompts / sampling / roots 一概没做**。它们的语义都是「让模型读你的文件、读你的提示词」，而这个项目的定位是「让你指挥管家」。要做也该是另一个项目。
- **stdio 传输没做**。有些 MCP 客户端默认走 stdio（起一个子进程说 JSON），这里只做 HTTP——因为 stdio 意味着客户端要能启动 `Dragon Butler.exe`，而它是个 GUI 程序，还会弹 UAC。README 里写明了「客户端要选 HTTP 类型」。
- **不做「自然语言解析」**。模型自己会解析，接口只要把能力说清楚就够了。在服务端再写一层意图识别，等于替所有客户端做它们更擅长的事。
