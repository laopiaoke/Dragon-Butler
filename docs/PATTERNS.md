# 交互模式（PATTERNS）

十一条已经定下来的模式。**新增或改动任何界面，先过一遍这张清单。**

每一条都是「要么做，要么说明为什么这次不做」。默默跳过 = 验收不过。

---

## 1. 流程类界面：底部必须有「下一步预告」

**是什么**：任何多步骤的流程（向导、批量设置、导入），在底部按钮旁边要有一句话，
告诉用户下一步会发生什么、他要准备什么。

**为什么**：多步骤界面里，人最怕的是「点下去会出来什么」。
一句预告能消掉这一半的犹豫，而且它比一个进度条便宜。

**已有的例子**（照这个写）：
> 已选 1 个。下一步给它们找主程序。

**自查**：
- [ ] 底部有这句话吗？
- [ ] 它说的是**下一步会发生什么**，不是「请点击下一步」这种废话？
- [ ] 它用的是事实（已选 1 个），不是鼓励（太棒了，继续吧）？

---

## 2. 需要验证的配置：旁边必须有「立即试一下」类按钮

**是什么**：任何填了之后「不知道通不通」的配置项（Webhook 地址、推送渠道、路径、端口），
旁边要有一个当场能验证的按钮，验证结果直接显示在那附近。

**为什么**：这类配置的错误都是延迟暴露的——用户填完关掉，等到第二天没收到推送才发现。
把验证提前到填写现场，是把一次「事后排查」换成一次「当场确认」。

**已有的例子**：
> 「发一条试试」——点了真的发一条，结果就写在旁边。

**自查**：
- [ ] 这个配置填错了，用户多久能知道？
- [ ] 如果超过「下一次运行」，那这里就该有个按钮？
- [ ] 按钮点了之后，结果是不是写在**原地**，而不是弹一个窗？

---

## 3. 错误卡：必须双 CTA（看详情 + 立即修复）

**是什么**：任何表示「出问题了」的卡片，都要给两个出口：
- **次按钮：看详情** —— 去看当时的日志、截图、现场。
- **主按钮：立即修复** —— 做一个能直接消掉这个问题的动作。

**为什么**：只给「看详情」是把排查工作丢回给用户；只给「立即修复」是让他闭着眼睛按。
两个一起给，才有「我明白了」和「我处理了」两步。

**已有的例子**：
> 主卡出错态：主按钮「看现场」/`tool.snapshot`，次按钮「重试这一轮」/`run.queue`。

**自查**：
- [ ] 两个按钮都有吗？
- [ ] 「看详情」通向的是**这一次**的具体现场，不是一个大而全的日志列表？
- [ ] 「立即修复」做的事，和这张卡说的问题是同一件吗？

---

## 4. 任何默认值：旁边必须解释 why

**是什么**：凡是程序替你选好的值（默认不推送、默认 8 点、默认 2 分钟间隔、默认跳过继续），
在它旁边写一句「为什么是这个」。

**为什么**：默认值是产品替用户做的一次决定。不解释的默认值，用户只会当成限制；
解释过的默认值，用户才会觉得这是有人替他想过。

**已有的例子**：
> 「默认什么都不弹——挂机时每跑完一个工具就弹一次，比不提醒更烦。」

**自查**：
- [ ] 这个值是不是程序选的（不是用户填的）？
- [ ] 旁边有「为什么」吗？
- [ ] 这句「为什么」说的是**场景**（挂机时、半夜、第一次用），不是「为了优化体验」？

---

## 5. 删除管理界面：先列能力迁移清单，再删

**是什么**：要拆掉一个独立的窗口 / 弹窗 / 一整片界面之前，先把**它一个人扛着的那些能力**
逐条写下来（左键做什么、双击做什么、右键有什么、怎么排序、怎么添加、状态在哪看），
每一条都先在新界面上实现并勾掉，最后才允许删旧的那块。

**为什么**：管理界面通常不是一次设计的，是一年年加出来的。直接删，「删除」这个动作看起来
干净利落，实际上是**能力真空期**——用户当天就会发现「双击没反应了」「换不了顺序了」。
先立后破的顺序不是洁癖，是让每一步都可回退。

**已有的例子（v1.42 拆「托管配置」窗口）**：

| 旧窗口里的能力 | 搬到哪 |
| --- | --- |
| 左键单击改启动设置 | 工具行展开区里的「编辑…」+ 右键「编辑…」 |
| 双击直接启动 | 双击工具行＝立即跑这一个 |
| 右键今晚跑不跑 / 移除 | 右键菜单（`今晚不跑它` ⇄ `今晚跑它`、`移除…`） |
| 拖拽换顺序 | 行首 `≡` 手柄上下拖 |
| ＋ 添加 | 列表末尾虚线「＋ 添加工具」（内联图标网格） |
| 已就绪 / 未配置 | 行内徽章（`✓ 已就绪` / `未配置路径`） |

六条全部在新界面上跑通之后，`TrayConfigWindow` 才被删。

**自查**：
- [ ] 这个界面一共扛了几件事？写下来了吗？
- [ ] 每一件都能在**别处的哪个具体位置**做吗？（「差不多能做」不算）
- [ ] 迁移清单里有没有一条是「只有这里能做」？那这条要么搬走，要么这次不删。
- [ ] 删掉之后，旧入口有没有留下死引用（事件绑定、命令 id、探针断言）？

## 6. 验证工具自己的完整性：入口表 + 金丝雀

探针、样例、脚本这类「验证别人」的东西，最容易出的毛病是**它自己悄悄少跑了一段**：
少注册一个组、漏加一个分支、跳过一条断言——全都不会报错，只会安静地少测一件事。
而少测的那条，往往正好是最危险的那条（比如「崩溃不许当成功」）。

**做法**：把入口从 `switch` 换成一张显式表，再配两个数字——

1. `CiGroups`：CI 点名的每一组，必须在表里。缺一个就红。
2. `ExpectedModeCount`：入口总数写死成一个常量。表里数量变了就红，逼你确认「是不是真加了」。

两处都查：建表后立刻查一次，跑完再查一次。**用退出码红，不要只打一行日志**——
日志会被 `| Select-Object -Last 3` 截掉，退出码不会。

**自查**：
- [ ] 入口表是显式的吗？（不是 `switch` + `default: return 0`）
- [ ] CI 跑的那几个名字，都在表里吗？有断言守着吗？
- [ ] 总数有常量守着吗？加了一项会不会忘了改？
- [ ] 反向验过一次吗？（临时删一项，确认真的红，再还原）

## 7. 源码级断言用宽容匹配，禁整串字面量

有些约束只能读源码来验：小条不大于多少、某个开关没被删、某个方法里没有下载调用。
这类断言最脆的地方是**它把整行源码抄进了断言**——那一行改个空格、换个判断顺序、
加个前置条件，断言就红，而实际约束一条都没破。

**做法**：断言只锁「意思」，不锁「写法」。

- 用**切片**取范围：`SliceBetween(text, "private void Window_Closing(", "\n    }")`，
  而不是 `text.Contains("…整行原文…")`。
- 在切片里用**正则**取要素：`Regex.IsMatch(block, @"if\s*\([^)]*StayInTray")`。
- 断言失败时把**实际取到的片段**打出来，否则下次还得人肉去猜它为什么红。
- 反向验一次：把那一行往无害的方向改（调换条件顺序、加空格），断言应当仍然绿。

**已有的例子**：v1.12 的 `uirules` 把 `Window_Closing` 那行原文整串写进断言；
外部贡献者一次「加了个 `|| !StayInTray` 的前置条件」——语义没变——就把它打成红的，
CI 红了整整一个提交（`dd1a81b` 改成 `SliceBetween` + 正则两段才修好）。

**自查**：
- [ ] 断言里有没有一整行、甚至多行源码原文？
- [ ] 换个等价写法（空格、顺序、局部变量）会不会红？
- [ ] 红了的时候，输出里有没有原始片段能看？

## 8. 低频的调试类入口，不进主页

**是什么**：那些「配一次就不管了」或「出问题才用得上」的东西——工具主程序路径、完成方式、
日志规则、现场包份数——放在主页会让**每天都要用的东西**给它们让位置。

**为什么**：主页要回答的是「今晚跑什么、跑不跑得成」。一张卡上挤进两种问题，两种都答不好：
第一次用的人找不到重点，用了半年的人每天要往下滚过去看一眼别人的答案。

**已有的例子**：v1.47 把「每个工具怎么跑」整块从主页任务清单卡搬到
设置页第六张卡「工具配置」——主页那张卡现在只回答一件事。

**自查**：
- [ ] 这个入口是「每天都动」还是「配一次就不管」？
- [ ] 它占的是主页的位置，还是设置二级页的位置？
- [ ] 搬走之后，主页那张卡是不是只剩一个主题？

## 9. 说明性、边界性的信息，收成副标题后面的 ⓘ

**是什么**：一段「能做什么、不能做什么」「为什么这样设计」的长说明，不铺成一张卡，
而是缩成一行副标题 + 一个 ⓘ，点开才是全文。

**为什么**：长说明对**第一次来的人**有用，对**第 20 次来的人**是每天都要跨过去的障碍。
收进 ⓘ 两拨人都照顾到了——想读的点开，不想读的一眼扫过。

**已有的例子**：v1.47 插件页把「插件怎么装」和「能做什么、不能做什么」两张整卡
收进副标题「安装、启用和配置插件 ⓘ」，**文字一句没删、一处没改**。

**自查**：
- [ ] 这段文字是每次来都要读的，还是读一次就够的？
- [ ] 收进 ⓘ 之后，原文是不是**一字未减**？（减了就是删功能，不是改版式）
- [ ] ⓘ 后面有没有一句说清「里面是什么」的提示？

## 10. 要断言的逻辑，抽成 public 纯函数

**是什么**：一段判断（端口合不合法、时间怎么算、文案怎么拼）如果只活在一个按钮的回调里，
探针就够不到它，只能退而求其次去读源码字符串。把它抽成 `public static` 纯函数之后，
探针可以直接给一组输入看输出。

**为什么**：读源码字符串的断言验的是「这行代码还在」，纯函数的断言验的是「这件事做对了」。
前者在重构面前一律误报，后者才是真的闸门。

**已有的例子**：`WebhookHub.ValidatePortText`（v1.44）——端口校验从输入弹窗里抽出来，
探针直接断言 1024/65535 边界、非数字、空值、前后空格。

**自查**：
- [ ] 这条断言现在验的是「行为」还是「文本」？
- [ ] 这段逻辑能不能抽成不碰 UI 的纯函数？
- [ ] 抽出来之后，原来的调用点有没有改成调它（而不是留一份副本）？

## 11. 大文件改完，先核对完整性再继续

**是什么**：改 `MainWindow.xaml` 这种三万行的文件，改完立刻验一遍——XML 能不能解析、
控件清点对不对、行数与字节数是不是在预期范围。**别等编译**，编译只会告诉你第一个错。

**为什么**：这个仓库里已经被同一种事故咬过两次（PowerShell 拼接丢半截 XAML），
两次都是「写完就往下走」，等到编译报一堆九曲十八弯的错才发现文件早就少了一半。

**做法**：
- XAML 改完 `XmlDocument.Load()`，过了才继续。
- 关键控件按名字清点一遍（`ToolRowHost`、`WrapUpBar`、`SecTools` …），确认该在的都在。
- 行数/字节数与改前对比，差异应该和这次改动**量级相当**；差一个数量级就是出事了。
- 出事就 `git checkout -- <文件>` 重来，不要在可疑状态上叠加改动。

**自查**：
- [ ] 改完立刻验了吗？（不是「等下一起验」）
- [ ] 验的是结构（解析、控件清点），不只是「文件还在」？
- [ ] 大小变化和这次改动对得上吗？
