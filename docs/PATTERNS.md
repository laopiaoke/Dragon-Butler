# 交互模式（PATTERNS）

四条已经定下来的模式。**新增或改动任何界面，先过一遍这张清单。**

每一条都是「要么做，要么说明为什么这次不做」。默默跳过 = 验收不过。

---

## 1. 流程类界面：底部必须有「下一步预告」

**是什么**：任何多步骤的流程（向导、批量设置、导入），在底部按钮旁边要有一句话，
告诉用户下一步会发生什么、他要准备什么。

**为什么**：多步骤界面里，人最怕的是「点下去会出来什么」。
一句预告能消掉这一半的犹豫，而且它比一个进度条便宜。

**已有的例子**（照这个写）：
> 已选 1 个。下一步给它们找主程序。

**自查**：
- [ ] 底部有这句话吗？
- [ ] 它说的是**下一步会发生什么**，不是「请点击下一步」这种废话？
- [ ] 它用的是事实（已选 1 个），不是鼓励（太棒了，继续吧）？

---

## 2. 需要验证的配置：旁边必须有「立即试一下」类按钮

**是什么**：任何填了之后「不知道通不通」的配置项（Webhook 地址、推送渠道、路径、端口），
旁边要有一个当场能验证的按钮，验证结果直接显示在那附近。

**为什么**：这类配置的错误都是延迟暴露的——用户填完关掉，等到第二天没收到推送才发现。
把验证提前到填写现场，是把一次「事后排查」换成一次「当场确认」。

**已有的例子**：
> 「发一条试试」——点了真的发一条，结果就写在旁边。

**自查**：
- [ ] 这个配置填错了，用户多久能知道？
- [ ] 如果超过「下一次运行」，那这里就该有个按钮？
- [ ] 按钮点了之后，结果是不是写在**原地**，而不是弹一个窗？

---

## 3. 错误卡：必须双 CTA（看详情 + 立即修复）

**是什么**：任何表示「出问题了」的卡片，都要给两个出口：
- **次按钮：看详情** —— 去看当时的日志、截图、现场。
- **主按钮：立即修复** —— 做一个能直接消掉这个问题的动作。

**为什么**：只给「看详情」是把排查工作丢回给用户；只给「立即修复」是让他闭着眼睛按。
两个一起给，才有「我明白了」和「我处理了」两步。

**已有的例子**：
> 主卡出错态：主按钮「看现场」/`tool.snapshot`，次按钮「重试这一轮」/`run.queue`。

**自查**：
- [ ] 两个按钮都有吗？
- [ ] 「看详情」通向的是**这一次**的具体现场，不是一个大而全的日志列表？
- [ ] 「立即修复」做的事，和这张卡说的问题是同一件吗？

---

## 4. 任何默认值：旁边必须解释 why

**是什么**：凡是程序替你选好的值（默认不推送、默认 8 点、默认 2 分钟间隔、默认跳过继续），
在它旁边写一句「为什么是这个」。

**为什么**：默认值是产品替用户做的一次决定。不解释的默认值，用户只会当成限制；
解释过的默认值，用户才会觉得这是有人替他想过。

**已有的例子**：
> 「默认什么都不弹——挂机时每跑完一个工具就弹一次，比不提醒更烦。」

**自查**：
- [ ] 这个值是不是程序选的（不是用户填的）？
- [ ] 旁边有「为什么」吗？
- [ ] 这句「为什么」说的是**场景**（挂机时、半夜、第一次用），不是「为了优化体验」？

---

## 5. 删除管理界面：先列能力迁移清单，再删

**是什么**：要拆掉一个独立的窗口 / 弹窗 / 一整片界面之前，先把**它一个人扛着的那些能力**
逐条写下来（左键做什么、双击做什么、右键有什么、怎么排序、怎么添加、状态在哪看），
每一条都先在新界面上实现并勾掉，最后才允许删旧的那块。

**为什么**：管理界面通常不是一次设计的，是一年年加出来的。直接删，「删除」这个动作看起来
干净利落，实际上是**能力真空期**——用户当天就会发现「双击没反应了」「换不了顺序了」。
先立后破的顺序不是洁癖，是让每一步都可回退。

**已有的例子（v1.42 拆「托管配置」窗口）**：

| 旧窗口里的能力 | 搬到哪 |
| --- | --- |
| 左键单击改启动设置 | 工具行展开区里的「编辑…」+ 右键「编辑…」 |
| 双击直接启动 | 双击工具行＝立即跑这一个 |
| 右键今晚跑不跑 / 移除 | 右键菜单（`今晚不跑它` ⇄ `今晚跑它`、`移除…`） |
| 拖拽换顺序 | 行首 `≡` 手柄上下拖 |
| ＋ 添加 | 列表末尾虚线「＋ 添加工具」（内联图标网格） |
| 已就绪 / 未配置 | 行内徽章（`✓ 已就绪` / `未配置路径`） |

六条全部在新界面上跑通之后，`TrayConfigWindow` 才被删。

**自查**：
- [ ] 这个界面一共扛了几件事？写下来了吗？
- [ ] 每一件都能在**别处的哪个具体位置**做吗？（「差不多能做」不算）
- [ ] 迁移清单里有没有一条是「只有这里能做」？那这条要么搬走，要么这次不删。
- [ ] 删掉之后，旧入口有没有留下死引用（事件绑定、命令 id、探针断言）？

## 6. 验证工具自己的完整性：入口表 + 金丝雀

探针、样例、脚本这类「验证别人」的东西，最容易出的毛病是**它自己悄悄少跑了一段**：
少注册一个组、漏加一个分支、跳过一条断言——全都不会报错，只会安静地少测一件事。
而少测的那条，往往正好是最危险的那条（比如「崩溃不许当成功」）。

**做法**：把入口从 `switch` 换成一张显式表，再配两个数字——

1. `CiGroups`：CI 点名的每一组，必须在表里。缺一个就红。
2. `ExpectedModeCount`：入口总数写死成一个常量。表里数量变了就红，逼你确认「是不是真加了」。

两处都查：建表后立刻查一次，跑完再查一次。**用退出码红，不要只打一行日志**——
日志会被 `| Select-Object -Last 3` 截掉，退出码不会。

**自查**：
- [ ] 入口表是显式的吗？（不是 `switch` + `default: return 0`）
- [ ] CI 跑的那几个名字，都在表里吗？有断言守着吗？
- [ ] 总数有常量守着吗？加了一项会不会忘了改？
- [ ] 反向验过一次吗？（临时删一项，确认真的红，再还原）
