# 插件计划：高风险功能怎么挂进来

> 你原话：「高风险的先不做，但加入计划表，可能有些高强度的用户用得上，改成插件或者其他的方式
> 在不影响本体的情况下作为插件添加进去。」
>
> 这份文件回答三件事：**为什么拆成插件**、**插件能拿到什么**、**五项各自长什么样**。

---

## 一、为什么是插件，不是开关

本体里加一个「我自己承担风险」的勾选框，技术上最省事，但有两个真问题：

1. **代码在里面，就一定会被读、被改、被误解。** 米游社签到要存 Cookie，多账号要轮换登录态——
   这些逻辑一旦进了主仓库，每个来提 issue 的人都会问「我能不能用」，而答案永远是「能，但你别用」。
2. **故障会污染主流程。** 一个跑在 `MainWindow` 进程里的 Cookie 泄漏，和主程序崩溃是同一件事：
   用户看到的是「一条龙管家坏了」，不是「那个插件坏了」。

插件的价值不在技术，在**边界是可见的**：装了什么、谁提供的、坏了影响谁，用户一眼能看到。

## 二、插件能拿到什么，拿不到什么

| 拿到 | 怎么给 | 为什么给 |
|---|---|---|
| 只读的运行状态 | `IPluginHost.Status`（`QueueService.IsRunning`、`CurrentToolId`、今日完成数、哨兵健康快照） | 「跑了没、跑到哪」是插件最常需要的信息，且是只读的 |
| 发通知 | `IPluginHost.Notify(level, title, message)` | 走既有的 11 个渠道，插件不自己实现推送 |
| 写自己的日志 | `IPluginHost.Log(text)` | 落到 `全部日志\plugin-{id}.log`，和主日志分开 |
| 自己的设置 | `IPluginHost.GetSetting(key)` / `SetSetting(key, value)` | 存 `config\plugins\{id}.json`，主设置里不出现插件字段 |
| 点一次「开跑」 | `IPluginHost.StartQueue()` | 同一个入口，不绕过 `QueueService` |

| 拿不到 | 为什么 |
|---|---|
| 主程序的 UI 控件树 | 一旦能改界面，插件就能把主界面改成任何样子，「不影响本体」不成立 |
| `AppState.Settings` 直接引用 | 同上；插件读写自己的配置文件，主设置结构不因插件而变 |
| 任意文件路径读写 | 只能读写自己目录下的东西。要读 BGI 日志就给一个只读的 `ReadBgiLog()` |
| 网络白名单之外 | 没有白名单。要用网络就得在插件自己的 `metadata.json` 里声明域名，安装时展示给用户看 |
| 静默安装 | 插件只能手动放进 `plugins\` 目录。没有「一键安装」，因为那等于替用户做决定 |

## 三、加载方式（三层隔离）

```
plugins\
  mihoyo-signin\
    Plugin.dll          ← 实现 IPlugin
    metadata.json       ← 名字 / 版本 / 作者 / 要访问的域名 / 要不要登录态
    ...
```

1. **独立 `AssemblyLoadContext`**：每个插件一个，`isCollectible: true`。插件抛异常、死循环、
   内存泄漏，都只影响它自己那个上下文，`Dispose` 之后可以被回收。
2. **启动时扫描，失败即跳过**：`metadata.json` 缺字段、版本不匹配、DLL 加载失败——统统只记一行
   日志，主界面照常启动。**一个坏插件不能让主程序打不开。**
3. **调用包在 `try/catch` 里，且带超时**：`Initialize` / `Tick` 都跑在后台线程，超过 10 秒没返回
   就标记这个插件「无响应」，不再调它。

界面上，高级设置里多一行「插件」：装了 N 个 / 没装。点开是列表（名字、作者、它要什么权限、
这次加载成功没有、日志入口）。**没装插件的用户永远看不到这一行**——和配置组合那一行同一个道理。

## 四、五项各自长什么样

| # | 插件 | 它能干什么 | 它必须要什么 | 本体给它的支持 | 什么时候值得做 |
|---|---|---|---|---|---|
| H1 | **米游社多账号签到** | 多账号每日签到 + 结果汇总 | 存 Cookie（本地加密），要访问 `api-takumi.mihoyo.com` | `GetSetting` 存凭据、`Notify` 报结果 | 有人明确要，且愿意自己承担账号风险 |
| H2 | **抽卡记录同步** | 读本地/URL 的祈愿记录，出统计 | `authkey`（敏感）、要访问米游社接口 | `ReadBgiLog` 拿本地记录路径、`GetSetting` 存链接 | 同上；这个比 H1 更敏感，因为它拿到了 authkey |
| H3 | **自动切号** | 切游戏账号再跑日常 | 改游戏登录态 | `Status` 知道队列在跑、`StartQueue` 触发 | **不建议做**：切错号的代价是跑到别人号上，而这个错误插件没法自己发现 |
| H4 | **WebDAV / 仓库中转 / 代理** | 多机同步配置、走代理 | 网络出口、第三方存储凭据 | 只需要 `GetSetting` 与网络声明 | 有人真的在两台机器上跑 |
| H5 | **远程桌面 / Maa / OBS** | 接外部程序 | 那三个程序本身 | 只能 `Process.Start`，本质和「跑完打开程序」一样 | 可以先不做——现有的「跑完打开程序」已经能覆盖大部分 |

**排序理由**：H3 排在「不建议」不是因为难，是因为**它的失败模式插件自己看不见**（跑到别人号上了，
从插件视角一切正常）。H5 排最后是因为本体已经有替代路径。

## 五、触发条件：什么时候真的动手

不做「先把框架搭好等插件来」——那会得到一个没人用的空壳和一堆维护成本。反过来，
等**同一个需求被三个人问过**再动手，那时候的接口才是被需求压出来的，不是想出来的。

在此之前，本体只做两件准备：

1. `plugins\` 目录扫描 + 加载失败不影响启动（骨架已经有了，`PluginHost.cs`）
2. 高级设置里那一行「插件」，装着 0 个时显示「没装」，装着时能看清单与日志

---

## 六、和本体其他部分的关系

- **不碰零 NuGet**：插件用独立目录，本体不引用任何插件 DLL，`csproj` 里没有 `ProjectReference`。
- **不影响双 exe 体积**：插件不进打包产物，用户自己放。
- **不影响探针**：插件加载器本身可以断言（缺 metadata、坏 DLL、版本不匹配都只跳过），
  但每个具体插件不做断言——它们不在仓库里。
