# v1.15 方案：把首屏做成「一眼知道该点哪」

> 目标不是「功能更多」，是**新用户第一次打开时不迷路**。ABGI 有 401 个端点、20+ 种定时任务、
> 完整的配置组工作台和 MCD 采集——功能密度极高，但它的首页是一张仪表盘：一进去就是十来个
> 数字和按钮，你得先知道自己在找什么才看得懂。
>
> 桌面端的优势恰恰相反：它是**别人电脑上的一个窗口**，用户只会给它三秒钟。
> 所以这一版不搬功能，搬**判断**——把 ABGI 里那些「要读文档才知道该配什么」的东西，
> 变成「打开就看到、看到就知道该点哪」。

---

## 一、先说清楚：从 ABGI 拿什么，不拿什么

| ABGI 有 | 我们要不要 | 理由 |
|---|---|---|
| 配置组工作台（收藏/排序/快速集） | **要**，但降到「拖拽排序 + 每天勾选」 | 配置组有几十个，人真正用到的永远是三五个。收藏=置顶，不需要单独的集合概念 |
| 定时任务（20+ 任务类型、cron 带秒） | **部分要**：只保留「每天一次 + 跑完再做一件事」 | cron 是给运维用的。游戏日常的周期就是「每天」，加个秒字段只是让人填错 |
| CD 感知采集、矿石统计、抽卡记录 | **不做** | 全是"看数据"的需求，本项目没有数据源，硬做只能做成假的 |
| 战斗策略 / 角色培养 | **不做** | 同上，且需要米游社账号与角色库 |
| 日志行为编排 | ✅ v1.14 已做（三档，非编辑器） | — |
| 通知模板变量 | **要**，但只做「一句话可改」 | 模板占位符是实现细节，不该让用户看见 |
| WebDAV 备份 / 仓库中转 / 团酱代理 | **不做** | 都是多机场景，本项目定位是单机常驻 |
| Maa / 远程桌面 / OBS | **不做** | 三个独立产品，接进来只会让安装包变大、出错面变多 |

**结论**：ABGI 的功能清单里有大约 80% 是"给已经会用的人"，本项目要抢的是剩下 20%——
即"第一次打开、只想让它今晚自己跑完"的人。

## 二、首屏重构（已出原型，见 `docs/proto/`）

### 现状问题

现在的主窗是"卡片流"：定时卡在左、队列卡在右，下面三张工具卡、自定义工具、高级设置、系统、通知。
结构本身没错，问题是**每张卡的信息权重一样**——未配置的工具卡和正在跑的队列卡占同样的高度和视觉重量。
新用户的第一眼看到的是一排"未配置"。

### 方案：一张会变的主卡

第一屏只有**一张主卡**，它按四种状态换内容（原型四张图就是这个）：

| 状态 | 主卡讲什么 | 主按钮 |
|---|---|---|
| 什么都没配 | "先告诉我在哪" + 三步指引，第一步高亮 | 选择 BetterGI.exe |
| 配好了没到点 | "今晚 23:30 自己开跑" + 还有多久 + 三个可改项 | 现在就开跑 |
| 正在跑 | "日常 · 已跑 18 分钟" + 进度条 + 预计 | 停下 |
| 跑完了 | "跑完了，46 分钟" + 对比往常 + 明天几点 | 看今天 |

下面才是"今天要跑什么"队列，再下面是三张小卡（守护 / 通知 / 今天）。
**原来的工具卡折叠进队列行**——因为工具卡的唯一作用就是"填路径"，而这件事一个引导步骤就够了。

### 为什么这样更好

- 第一眼只有一件事要做。有且仅有一个主按钮是青绿色，其余都是灰描边
- 状态用"人话"写，不写字段名。"已就绪"改成"已就绪"没用，改成"今晚 23:30 自己开跑"才有用
- 主卡是**同一块区域换内容**，不是四张卡片轮流出现——位置固定，用户第二次打开直接知道往哪看

### 需要你确认的三点

1. **工具卡真的折叠掉？** 现在三张工具卡占掉一屏的三分之一，信息量却只有"路径填没填"。
   折叠进队列行（点行展开配置）能不能接受？
2. **主卡四种状态够不够？** 还有第五种——"出错了"。我倾向把它也做成主卡的一种状态
   （红框 + 一句人话 + 一个"重试"按钮），而不是弹窗或通知栏。
3. **三张小卡放哪些？** 原型放了"守护 / 通知 / 今天"。也可以换成"守护 / 最近告警 / 今天"。

## 三、功能计划，按风险分三档

### 🟢 低风险：只读本地文件、只改自己的配置（可以直接做）

| # | 功能 | 对应 ABGI | 落点 |
|---|---|---|---|
| L1 | **首屏主卡四态** | —（差异化） | 改 `MainWindow.xaml` 第一屏结构，新增 `HomeState.cs` 纯函数决定状态 |
| L2 | **工具行内联配置** | `bgiConfig/allConfig` | 队列行点开 → 选 exe / 选配置组 / 选每天哪几天 |
| L3 | **一键"就用默认"** | `bgiConfig/options` | 首次引导的第二步：时间默认 08:00、周三不跑（游戏周常），可一键跳过 |
| L4 | **配置组收藏与排序** | `scriptGroup/workspace` + `groupPreference` | 配置组切片窗口里加置顶（★），置顶的排前面；存 `AppSettings` |
| L5 | **跑完再做一件事的扩展** | `taskCron/*` | 现有只有 通知/睡眠/关机，加"再跑一轮指定工具""打开某个程序" |
| L6 | **通知模板只暴露一句话** | `notice/template/context` | 现在通知正文是硬编码的；改成可编辑的一行，占位符在下面列成小字 |

这六项全都不碰进程之外的东西，都能在 `tests\CoordinatorProbe` 写断言（`Scan`/`Decide`/`Parse` 都是纯函数）。

### 🟡 中风险：会启动/关闭别的程序，或者写 BGI 的配置文件（要先给你看计划）

| # | 功能 | 对应 ABGI | 风险点 | 缓解 |
|---|---|---|---|---|
| M1 | **改一条龙配置** | `bgiConfig/saveConfig`（有 revision 乐观并发） | 直接写 BGI 的 json，写坏了他今晚就跑不成；BGI 运行时写还有覆盖风险 | ①只能改**我们自己建的副本**，不碰用户手写的配置 ②写前备份到 `config\bgi-backup\{stamp}` ③BGI 在跑就拒绝写，只提示"先关掉再改" ④不做 revision，因为我们是单机单进程，用文件 mtime 兜底 |
| M2 | **跑完自动关机/睡眠/重启** | `taskCron/AtOnceRun` | 已经在做（v1.6），扩展后可能误触 | 保持"只在队列成功结束后触发"，加 60 秒可撤销倒计时 |
| M3 | **自动重启 BGI** | `TaskCron` 里的重启类 | 已在做（`AutoRestartBgi`），60 秒冷却 | 加一个"今天已经重启过 N 次就停手"，防止无限重启把机器拖死 |
| M4 | **脚本队列定时执行** | `taskCron/scriptQueues` | 要读 BGI 的脚本目录结构，那个结构会随 BGI 版本变 | 只做"沿着现有 `QueueService` 跑我们自己的队列"，不解析 BGI 脚本格式 |
| M5 | **清理/更新 BGI 自身** | `uploadBgi` / `aBgiUpdateService` | 替换正在运行的 exe | 只做"检查有没有新版，给个链接"，**不自动下载替换** |

### 🔴 高风险：多账号、凭据、外部服务（我建议这一版不做，先列出来给你判断）

| # | 功能 | 对应 ABGI | 为什么算高风险 |
|---|---|---|---|
| H1 | **米游社多账号签到** | `mysSignIn` / `Mihoyo/*` | 要存 Cookie/authkey，等于替用户保管登录态；多账号轮换有风控风险，没人验证过 |
| H2 | **抽卡记录同步** | `gacha/sync` | 祈愿链接里的 `authkey` 是敏感凭据，存本地就是一份可被盗的资产 |
| H3 | **自动切号** | `BagStatistics/accounts` | 切换账号会改游戏登录态，切错号会导致当天的日常跑到别人号上 |
| H4 | **WebDAV / 仓库中转 / 代理** | 对应章节 | 引入网络出口与第三方存储，出错面大，且与本项目"单机常驻"定位冲突 |
| H5 | **远程桌面 / Maa / OBS** | 对应章节 | 三个独立产品，接进来会让安装包变大、故障定位变难 |

**我的建议**：H1–H5 这一版全部不做。理由不是"不敢"，是**它们都不降低门槛**——
真正让新用户卡住的是"不知道点哪"，不是"功能不够多"。等功能密度撑不住了再谈。

### M1 为什么停在内核

写配置的**风险控制全部实现了**：先备份、备份失败就整个放弃、写到临时文件再原子替换、BGI 在跑就拒写、mtime 变了就拒写、路径必须在 `User\OneDragon` 下。

停住的是最上面一层：`settings.completionAction` 这个键的**合法取值集合不知道**。ABGI 文档只写「结束后的行为，包括关机等高风险动作」，没列枚举。这意味着我能写进去，但不知道自己写的是不是 BGI 认识的值——写坏了今晚就跑不成，而这正是当初说要防的事。

两条路，等你选：

- **A（保守）**：函数留着，界面不暴露。等哪天能拿到真实的 BGI 配置样本或更新后的文档再说。
- **B（可用）**：接开关，但候选值**只从既有配置里读出来**，只允许在「这台机器上已经出现过的取值」之间切。读不到就不显示这项。

我倾向 A：M1 的其他部分（备份、原子写、拒绝在运行中写）本身有价值，但「改一条龙配置」这件事如果没有真实的取值表，等于让用户在不懂的选项里挑一个。

### 高风险五项的处理

按你说的，不做进本体，改成**插件挂载点**。计划表在 `docs/plans/插件计划.md`。
